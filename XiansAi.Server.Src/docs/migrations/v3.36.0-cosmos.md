# v3.36.0 — Cosmos DB Migration

Two unique indexes on `users` can block all user provisioning on Azure Cosmos DB, and both have to be
dropped by hand. Neither is dropped automatically: the index synchronizer skips dropping unused
indexes on Cosmos, and it only ever *creates* indexes whose name is missing — it never reconciles an
index whose definition changed while its name stayed the same.

1. `linked_identities_subject_authority_unique` — new in this release cycle and now obsolete, since
   linked provider identities moved out of the `users` document into their own
   `user_linked_identities` collection.
2. `email_1` — declared `unique: true` in July 2025 and corrected to non-unique three days later.
   Deployments created in that window still carry the unique version.

Plain MongoDB deployments need nothing for the first: the synchronizer drops it on startup. **The
`email_1` correction has never applied anywhere**, on Cosmos or MongoDB, because the name did not
change — check for it regardless of database engine.

## Who is affected

List the indexes and compare against `mongodb-indexes.yaml`:

```javascript
db.users.getIndexes()
```

Only `_id_` and `user_id_1` should be `unique`. If either
`linked_identities_subject_authority_unique` or a unique `email_1` appears, the symptom is that
**no new user can sign in**, with this repeating in the log:

```text
fail: Shared.Services.UserTenantService[0]
      Failed to provision user ***@example.com: Failed to create new user
```

Both indexes fail the same way, and it is the way a unique index always fails on Cosmos: **only one
document may be missing the indexed field**, because [a missing field counts as null toward the
constraint](https://learn.microsoft.com/en-us/azure/cosmos-db/unique-keys).

`linked_identities_subject_authority_unique` was declared `sparse` so that users without links stayed
out of it, but Cosmos does not implement sparse unique indexes, so every user created after the first
collides on `(null, null)`.

A unique `email_1` breaks provisioning for users who arrive **without an email claim**. Their record
is written with an empty email, and `CreateNewUser` deliberately skips its email-collision check for
blank values — correctly, since blank emails are not meant to be unique — so the insert proceeds and
the index rejects it. Sign-ins that do carry an email are unaffected, which is why this can sit
dormant for a long time and then surface when one identity provider stops sending the claim.

## Migration

Run these against the application database before or immediately after deploying v3.36.0. Existing
users are unaffected; only provisioning of new ones is broken while the old index exists.

**1. Copy any existing links into the new collection.** Most deployments have none — the feature is
recent — but check rather than assume, as dropping the index does not delete the embedded data:

```javascript
db.users.find({ linked_identities: { $exists: true, $ne: [] } }).forEach(u => {
  u.linked_identities.forEach(li => {
    db.user_linked_identities.insertOne({
      subject:   li.subject,
      authority: li.authority,
      user_id:   u.user_id,
      linked_at: li.linked_at,
      linked_by: li.linked_by
    });
  });
});
```

Run this *before* the new unique index exists, or duplicates in the old data will abort the loop
partway. If the deployment has already started v3.36.0, the index is in place and any rejected insert
is a genuine conflict to resolve by hand.

**2. Drop the old index.**

```javascript
db.users.dropIndex("linked_identities_subject_authority_unique")
```

**3. Remove the now-unused embedded field.**

```javascript
db.users.updateMany({}, { $unset: { linked_identities: "" } })
```

**4. Replace a unique `email_1`.** Skip if `getIndexes()` did not report it as unique. Check first
how many records would have collided, purely to know what you are looking at — more than one means
provisioning has been failing for every email-less sign-in:

```javascript
db.users.countDocuments({ $or: [{ email: "" }, { email: null }, { email: { $exists: false } }] })
db.users.dropIndex("email_1")
```

The application recreates `email_1` non-unique at startup, from the YAML. Uniqueness of real email
addresses does not depend on the index: `CreateNewUser` refuses to create a user whose email already
belongs to another account, which is the check that should be enforcing it.

**5. Verify.** After the application has started:

```javascript
db.users.getIndexes()
db.user_linked_identities.getIndexes()
```

On `users`, only `_id_` and `user_id_1` should be unique. On `user_linked_identities`, expect
`subject_authority_unique` and `user_id_1` — the application creates both at startup on an empty
collection, which is what satisfies Cosmos's requirement that a unique index be created before the
collection holds data. Then confirm a new user can sign in and that the provisioning failures have
stopped.

## Rollback

Rolling back to the previous version restores the old index on startup and, on Cosmos, reintroduces
the provisioning failure. If you must roll back, drop the index again afterwards and accept that
linking is unavailable until you roll forward. Links written to `user_linked_identities` are not read
by the older build, but are left intact and resume working on the next upgrade.
