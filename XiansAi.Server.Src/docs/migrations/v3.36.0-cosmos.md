# v3.36.0 — Cosmos DB Migration

Linked provider identities moved out of the `users` document into their own
`user_linked_identities` collection. On Azure Cosmos DB this requires one manual step, because the
index synchronizer does not drop unused indexes on Cosmos and the old index will otherwise remain and
block all user provisioning.

Plain MongoDB deployments need nothing: the synchronizer drops the old index on startup.

## Who is affected

Cosmos DB deployments that ran any build carrying the `linked_identities_subject_authority_unique`
index on `users`. Check for it:

```javascript
db.users.getIndexes().filter(i => i.name === "linked_identities_subject_authority_unique")
```

Empty result means there is nothing to do. If the index is present, the symptom is that **no new user
can sign in**, with this repeating in the log:

```text
fail: Shared.Services.UserTenantService[0]
      Failed to provision user ***@example.com: Failed to create new user
```

The index is unique over `linked_identities.subject` and `linked_identities.authority` and was
declared `sparse` so that users without links stayed out of it. Cosmos DB does not implement sparse
unique indexes — [a missing field counts as null toward the
constraint](https://learn.microsoft.com/en-us/azure/cosmos-db/unique-keys), so only one user document
may lack the field. Every user created after the first collides on `(null, null)`.

## Migration

Run these against the application database before or immediately after deploying v3.36.0. Existing
users are unaffected; only provisioning of new ones is broken while the old index exists.

**1. Copy any existing links into the new collection.** Most deployments have none — the feature is
recent — but check rather than assume, as dropping the index does not delete the embedded data:

```javascript
db.users.find({ linked_identities: { $exists: true, $ne: [] } }).forEach(u => {
  u.linked_identities.forEach(li => {
    db.user_linked_identities.insertOne({
      subject:   li.subject,
      authority: li.authority,
      user_id:   u.user_id,
      linked_at: li.linked_at,
      linked_by: li.linked_by
    });
  });
});
```

Run this *before* the new unique index exists, or duplicates in the old data will abort the loop
partway. If the deployment has already started v3.36.0, the index is in place and any rejected insert
is a genuine conflict to resolve by hand.

**2. Drop the old index.**

```javascript
db.users.dropIndex("linked_identities_subject_authority_unique")
```

**3. Remove the now-unused embedded field.**

```javascript
db.users.updateMany({}, { $unset: { linked_identities: "" } })
```

**4. Verify.** After the application has started, the new collection should carry its unique index:

```javascript
db.user_linked_identities.getIndexes()
```

Expect `subject_authority_unique` and `user_id_1`. The application creates both at startup, on an
empty collection — which is also what satisfies Cosmos's requirement that a unique index be created
before the collection holds data. Then confirm a new user can sign in and that the provisioning
failures have stopped.

## Rollback

Rolling back to the previous version restores the old index on startup and, on Cosmos, reintroduces
the provisioning failure. If you must roll back, drop the index again afterwards and accept that
linking is unavailable until you roll forward. Links written to `user_linked_identities` are not read
by the older build, but are left intact and resume working on the next upgrade.
